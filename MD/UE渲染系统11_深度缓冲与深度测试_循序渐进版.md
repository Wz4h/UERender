# UE 渲染系统 11：深度（Depth）与可见性判断

## 本节学习目标

在前面的课程中，我们已经学习了：

- 三角形经过 Rasterization 后，会产生 Fragment。
- Pixel Shader 根据材质规则计算当前表面的属性。
- Deferred Rendering 会把表面属性保存到 GBuffer，供后续 Lighting 使用。

但这里还缺少一个关键问题：

> 如果多个物体投影到屏幕上的同一个位置，GPU 怎么知道应该显示哪一个？

这就是本节要解决的问题。

学完本节，你应该能够解释：

1. 为什么渲染需要深度信息？
2. Depth Buffer 保存什么？
3. Depth Test 和 Depth Write 分别做什么？
4. Early-Z 为什么能够减少 Pixel Shader 的工作？
5. Depth PrePass 为什么有时能提高性能？
6. Fragment 的深度从哪里来？
7. 为什么透视深度不是线性的？什么是 Z-Fighting 和 Reverse-Z？

---

# 一、从一个最常见的画面问题开始：物体遮挡

想象摄像机前面有两个物体：

- 一个红色球体距离摄像机较近。
- 一个蓝色球体距离摄像机较远。

如果两个球体在屏幕上有重叠区域，那么重叠区域应该显示红色球体，而不是蓝色球体。

这件事看起来理所当然，但对 GPU 来说，它需要一个明确的判断依据。

## 1. 为什么不能只按照绘制顺序决定？

假设 GPU 先绘制蓝色球体，再绘制红色球体。

如果后绘制的颜色总是覆盖先绘制的颜色，那么结果刚好正确。

但如果绘制顺序反过来：

```text
先绘制红色球体
再绘制蓝色球体
```

蓝色球体就可能把前面的红色球体覆盖掉。

然而，蓝色球体明明在更远的位置。

所以：

> **绘制顺序不等于物体的前后关系。**

GPU 需要一种不依赖简单绘制顺序的机制，判断当前表面是否被更近的表面遮挡。

这个机制就是 Depth Test（深度测试）。

---

# 二、Depth 是什么？

在讨论深度测试之前，先明确“深度”描述的是什么。

可以先把它理解为：

> 一个表面相对于摄像机，在观察方向上有多远。

这里说的是沿摄像机观察方向的深度，不一定是物体到摄像机的直线距离。

例如，两个点可能处于同一个深度平面上，但它们离摄像机的直线距离不同。

因此，在图形渲染中，Depth 不是简单的三维距离。

## 1. 为什么需要把深度记录下来？

假设屏幕上的某个位置先后产生了三个 Fragment：

```text
Fragment A：较近
Fragment B：较远
Fragment C：最远
```

最终这个位置只能显示最前面的可见表面。

GPU 需要知道：

- 之前这个位置已经记录了多深？
- 当前 Fragment 比之前记录的表面更近，还是更远？

因此，需要有一个地方保存已经记录的深度值。

这个资源就是 **Depth Buffer（深度缓冲区）**。

---

# 三、Depth Buffer：保存深度的数据资源

Depth Buffer 是专门用于保存深度信息的 GPU 资源。

可以先把它想象成一张与屏幕位置对应的二维深度图。

例如，屏幕上有这些位置：

```text
屏幕位置       Depth Buffer 中记录的深度

(100, 200)     0.20
(101, 200)     0.35
(102, 200)     0.80
(103, 200)     0.42
```

每个位置记录的深度，代表当前已经写入该位置的表面深度。

注意：

- 这里的数值只是示意。
- 实际深度通常不是以“米”为单位。
- UE 常用的透视深度采用 Reverse-Z，数值方向与传统深度示例相反。

## 1. Depth Buffer 和 GBuffer 有什么区别？

前一节学习了 GBuffer，它们都与屏幕位置对应，但保存的数据不同。

| 资源 | 主要保存内容 |
|---|---|
| GBuffer | 表面属性，例如 BaseColor、Normal、Roughness、Metallic |
| Depth Buffer | 深度信息 |

可以这样理解：

```text
同一个屏幕位置
    │
    ├── GBuffer：这个表面是什么样？
    │
    └── Depth Buffer：这个表面有多深？
```

它们共同帮助后续渲染阶段理解当前可见表面，但不是同一个 Buffer。

---

# 四、Depth Test：判断当前 Fragment 是否通过深度测试

现在有了 Depth Buffer，GPU 就可以比较当前 Fragment 和已经记录的深度。

先用最容易理解的传统深度规则举例：

- 深度值越小，表示越近。
- 深度值越大，表示越远。

假设某个屏幕位置的 Depth Buffer 当前记录：

```text
Depth Buffer = 10
```

现在产生一个 Fragment：

```text
Fragment Depth = 5
```

比较：

```text
5 < 10
```

当前 Fragment 更近，因此通过深度测试。

如果开启深度写入，Depth Buffer 就会更新：

```text
Depth Buffer = 5
```

之后又产生一个 Fragment：

```text
Fragment Depth = 8
```

比较：

```text
8 > 5
```

当前 Fragment 更远，因此深度测试失败，它不能覆盖已经记录的近处表面。

## 1. 深度测试的基本流程

```text
产生 Fragment
      ↓
读取对应位置的 Depth Buffer
      ↓
比较当前 Fragment Depth
      ↓
是否通过？
   ↙       ↘
  通过      失败
   ↓         ↓
继续处理    丢弃相关结果
```

这里的“丢弃”是指当前 Fragment 不再作为这个位置的可见结果写入。具体哪些后续操作可以省略，还取决于深度测试的执行时机，下一部分会解释。

## 2. Depth Test 不等于 Depth Write

这是必须区分的两个概念。

**Depth Test：**

读取已有深度，比较当前 Fragment 是否通过。

**Depth Write：**

把当前 Fragment 的深度写入 Depth Buffer。

两者可以分别配置。

例如：

| 深度测试 | 深度写入 | 结果 |
|---|---|---|
| 开启 | 开启 | 先比较，通过后可以更新深度 |
| 开启 | 关闭 | 比较深度，但不更新深度 |
| 关闭 | 关闭 | 不进行普通深度比较，也不写入深度 |
| 关闭 | 开启 | 特殊配置，通常不是普通不透明物体的常见设置 |

因此：

> **通过 Depth Test 不代表一定会写入 Depth Buffer。**

普通不透明物体通常会开启深度测试和深度写入；半透明物体则经常需要深度测试，但通常不写入深度，以免影响后面其他透明层的绘制。具体仍取决于材质混合方式和渲染需求。

---

# 五、Depth Test 在什么时候执行？

到这里，我们知道 Depth Test 要比较深度。

但还有一个影响性能的问题：

> GPU 是先执行 Pixel Shader，再做深度测试；还是先做深度测试，再执行 Pixel Shader？

这就引出了 Early-Z 和 Late-Z。

## 1. Late-Z：较晚执行深度测试

假设当前 Fragment 的深度为 10，而 Depth Buffer 已经记录了 5。

当前 Fragment 明显被遮挡。

如果先执行 Pixel Shader，流程可能是：

```text
Fragment
    ↓
Pixel Shader
    ├── 采样 Texture
    ├── 计算 BaseColor
    ├── 计算 Normal
    └── 计算其他材质属性
    ↓
Depth Test
    ↓
发现测试失败
    ↓
丢弃结果
```

问题在于：

Pixel Shader 已经执行了，但最终结果却没有被使用。

如果材质很复杂，这些计算就可能造成浪费。

这类较晚执行深度测试的路径，通常称为 Late-Z。

## 2. Early-Z：提前执行深度测试

既然可以根据深度判断当前 Fragment 被遮挡，能不能在 Pixel Shader 执行之前就做这个判断？

如果能够确定它无法通过深度测试，就可以提前淘汰它。

```text
Fragment
    ↓
Early-Z：提前进行深度测试
    ↓
测试失败
    ↓
跳过 Pixel Shader
```

这样就省去了后续不必要的材质计算。

如果测试通过，Fragment 才继续执行后续着色工作。

## 3. Early-Z 和 Depth Test 的关系

不要把它们理解成两个互不相关的功能。

- Depth Test：要进行的深度比较。
- Early-Z：把深度测试尽可能提前执行。
- Late-Z：在较晚的阶段执行深度测试。

因此：

> **Early-Z 本身执行的就是深度测试。它改变的是测试时机，而不是深度比较的目的。**

## 4. Early-Z 是否意味着只有最终最前面的 Fragment 才执行 Pixel Shader？

不一定。

假设同一个屏幕位置依次遇到三个 Fragment，深度分别为：

```text
A：15
B：10
C：5
```

仍然使用传统深度规则：数值越小越近。

如果绘制顺序是 A、B、C：

| Fragment | 当时 Depth Buffer | 测试结果 | 是否可能执行 Pixel Shader |
|---|---:|---|---|
| A：15 | 初始远端值 | 通过 | 是 |
| B：10 | 15 | 通过 | 是 |
| C：5 | 10 | 通过 | 是 |

三个 Fragment 到达时，都比当时已经记录的表面更近，因此都可能通过 Early-Z。

最后虽然只留下 C，但 A 和 B 的材质计算可能已经执行过。

这说明：

> **Early-Z 只能利用当前已经存在的深度信息，不能提前知道之后还会出现哪个更近的 Fragment。**

这也解释了为什么有时还需要 Depth PrePass。

补充：Early-Z 是 GPU 的优化机制，是否能在某个 Shader 上发挥作用，取决于深度状态、Shader 行为和硬件实现。比如 Shader 自己输出深度、使用 discard/clip 或存在某些副作用时，早期深度测试和写入可能受到限制。这里先掌握基本原理即可。

# 六、Depth PrePass：提前准备深度数据

刚才的问题是：

如果先绘制远处物体，再绘制近处物体，那么远处物体可能已经执行了 Pixel Shader。

能不能先把场景中可见表面的深度准备好？

这就是 Depth PrePass 的思路。

**Depth PrePass 是额外增加的一个渲染 Pass，主要目的是提前生成或准备 Depth Buffer。**

## 1. 不使用 Depth PrePass

```text
Base Pass
    ↓
处理几何体
    ↓
Rasterization
    ↓
Fragment
    ↓
深度测试
    ↓
Pixel Shader
    ↓
输出材质结果
```

Depth Buffer 会随着正常绘制逐步建立。

## 2. 使用 Depth PrePass

先执行一次深度预处理：

```text
Depth PrePass
    ↓
处理相关几何体
    ↓
Rasterization
    ↓
深度测试与深度写入
    ↓
Depth Buffer
```

这一阶段通常不计算完整的材质和光照。

之后再执行正式的 Base Pass：

```text
Base Pass
    ↓
处理几何体
    ↓
Rasterization
    ↓
利用已有 Depth Buffer 进行深度测试
    ↓
尽可能提前淘汰被遮挡的 Fragment
    ↓
Pixel Shader
    ↓
输出材质结果
```

这样，正式绘制时，GPU 已经拥有较完整的深度信息。

## 3. Depth PrePass 与 Early-Z 的关系

两者不是同一个东西。

| 概念 | 所属层级 | 作用 |
|---|---|---|
| Depth Buffer | 数据资源 | 保存深度 |
| Depth Test | 测试机制 | 比较深度 |
| Early-Z | GPU 优化机制 | 提前进行深度测试 |
| Depth PrePass | 渲染流程中的 Pass | 提前准备深度数据 |

它们可以配合：

```text
Depth PrePass
    ↓
提前建立 Depth Buffer
    ↓
正式 Base Pass
    ↓
Early-Z 利用已有深度
    ↓
减少不必要的 Pixel Shader 工作
```

## 4. 为什么不永远开启 Depth PrePass？

因为 Depth PrePass 自己也有成本：

- 需要额外处理一次几何体。
- 需要额外的绘制和光栅化工作。
- 某些材质，例如 Masked 材质，可能仍需要执行 Pixel Shader 来判断是否覆盖像素。

因此它是一种成本交换：

```text
额外的深度预处理成本
        ↓
减少正式绘制中的像素着色成本
```

如果场景遮挡严重、材质着色昂贵，可能很划算。

如果场景很简单、遮挡很少，额外 Pass 可能得不偿失。

Depth PrePass 不是所有项目都必须使用的固定步骤，而是引擎根据渲染路径、项目设置和具体需求采用的策略。

# 七、Fragment 的深度从哪里来？

前面一直在使用 Fragment Depth，但它并不是模型顶点上直接保存的一个“最终屏幕深度值”。

要理解它，需要回到之前学习的坐标变换。

## 1. 从顶点位置开始

模型顶点最初有自己的 Position，例如：

```text
Vertex Position = (X, Y, Z)
```

这个位置通常处于模型局部空间。

在渲染过程中，会经过一系列坐标变换：

```text
Local Space
    ↓
World Space
    ↓
View Space
    ↓
Clip Space
```

其中：

- Local Space：模型自身的局部坐标。
- World Space：世界坐标。
- View Space：以摄像机为参考的观察空间。
- Clip Space：经过投影变换后的裁剪空间。

## 2. 投影变换带来深度映射

在 View Space 中，顶点已经处于以摄像机为参考的坐标系。

经过投影矩阵变换后，顶点进入 Clip Space。

随后进行透视除法：

```text
NDC.x = Clip.x / Clip.w
NDC.y = Clip.y / Clip.w
NDC.z = Clip.z / Clip.w
```

这里的 NDC 是 Normalized Device Coordinates（归一化设备坐标）。

深度值就是由投影后的深度分量进一步映射得到的，而不是直接把世界坐标 Z 当作 Depth Buffer 的值。

## 3. Rasterization 如何得到 Fragment Depth？

三角形经过裁剪、投影和光栅化后，会覆盖屏幕上的一系列 Sample。

GPU 根据投影后的顶点深度和当前 Sample 在三角形中的位置，计算对应的 Fragment Depth。

简化流程：

```text
Vertex Position
    ↓
Vertex Shader：坐标变换
    ↓
Projection
    ↓
Clip Space / NDC
    ↓
Rasterization
    ↓
Fragment Depth
    ↓
Depth Test
```

这也解释了：

> 为什么 Early-Z 可以在 Pixel Shader 执行之前进行深度测试？

因为 GPU 在光栅化阶段就能够得到用于深度测试的片元深度，不必等 Pixel Shader 把材质全部计算完。

注意：这里讲的是常规光栅化管线。Pixel Shader 也可以在特定情况下输出或修改深度，这会影响深度测试和写入的执行方式。

# 八、为什么 Depth 通常不是实际距离？

很多初学者会自然地认为：

```text
Depth = 摄像机到物体的实际距离
```

但通常不是。

Depth Buffer 保存的是投影后、映射到深度范围内的值。

以传统的透视深度映射为例：

```text
Near Plane → 0
Far Plane  → 1
```

例如：

```text
距离近裁剪平面：Depth 接近 0
距离远裁剪平面：Depth 接近 1
```

这样 GPU 就可以用一个有限范围内的数值进行深度比较。

## 1. Near Plane 和 Far Plane

摄像机的视锥体通常由近裁剪平面和远裁剪平面界定。

- Near Plane：距离摄像机最近的有效裁剪边界。
- Far Plane：距离摄像机最远的有效裁剪边界。

位于有效裁剪范围之外的几何体会受到裁剪规则影响。

需要注意：不同图形 API、投影矩阵和深度约定的 NDC 范围可能不同。这里先用传统的 0～1 深度映射帮助理解，后面再看 UE 的实际约定。

# 九、透视深度为什么是非线性的？

这是深度系统中非常重要的知识点。

在透视投影下，Depth Buffer 中的深度值与观察空间中的距离并不是简单的线性关系。

传统透视深度映射的一个直观特点是：

> 大量深度数值集中在靠近远裁剪平面的区域。

假设近裁剪距离为 1，远裁剪距离为 1000，使用传统深度映射，数值大致如下：

| 观察空间距离 | 传统深度值（约） |
|---:|---:|
| 1 | 0.000000 |
| 2 | 0.500501 |
| 10 | 0.900901 |
| 50 | 0.980981 |
| 100 | 0.990991 |
| 500 | 0.998999 |
| 1000 | 1.000000 |

可以观察到：

- 从 1 到 2，深度值变化很大。
- 从 500 到 1000，深度值变化很小。

这意味着远处物体的深度值可能非常接近。

而 Depth Buffer 的存储精度是有限的。

如果两个距离很近的表面被映射成非常接近的深度值，就可能难以稳定区分它们。

# 十、Z-Fighting：深度精度不足的表现

Z-Fighting（深度冲突）是常见的深度精度问题。

假设两个表面几乎重叠：

```text
表面 A：深度 0.998900
表面 B：深度 0.998901
```

它们的深度非常接近。

如果深度缓冲格式的精度不足，或者几何表面本身几乎共面，深度比较就可能无法稳定地区分两个表面。

画面中可能出现：

- 条纹状交错。
- 局部闪烁。
- 两个表面像是在争夺显示权。

这就是 Z-Fighting。

常见处理方向包括：

- 避免两个表面完全重叠或过于接近。
- 合理设置摄像机 Near Plane。
- 避免不必要地使用过大的 Far Plane。
- 使用更合适的深度格式和深度方案。

# 十一、Reverse-Z：为什么现代引擎会反转深度？

传统深度映射：

```text
Near → 0
Far  → 1
```

Reverse-Z 则反过来：

```text
Near → 1
Far  → 0
```

也就是说，越近的表面，深度值越大。

## 1. 为什么反转有帮助？

关键不只是把 0 和 1 对调，而是它与浮点数的精度分布配合。

浮点数在不同数值区间的精度并不是均匀的。

对于常见的浮点深度格式，靠近 0 的区域具有更密集的可表示数值。

传统透视深度把远处大量深度值挤在接近 1 的区域。

Reverse-Z 把远处映射到接近 0 的区域，于是可以更好地利用浮点数在该区域的精度分布。

结果是：

> **在使用合适浮点深度格式和投影设置时，Reverse-Z 能显著改善深度精度，尤其是远距离区域。**

仅仅把数值反过来，并不能让所有深度格式都获得同样的精度收益；它的优势与浮点深度格式和投影映射密切相关。

## 2. 传统深度与 Reverse-Z 对比

| 项目 | 传统深度 | Reverse-Z |
|---|---|---|
| 近处 | 0 | 1 |
| 远处 | 1 | 0 |
| 深度比较方向 | 通常较小值更近 | 通常较大值更近 |
| 常见清除值 | 1 | 0 |
| 主要目标 | 深度比较 | 改善浮点深度精度 |

UE 的常见透视渲染路径使用 Reverse-Z。

因此，学习 UE 时不能一直套用“深度越小越近”的传统示例。

前面用 5 米、10 米比较深度，只是为了理解遮挡关系；在 UE 实际的深度缓冲中，应该按照 Reverse-Z 的深度约定理解比较方向。

# 十二、在 UE 中观察深度

理论学完之后，可以在 UE 中做实验。

## 实验一：观察 SceneDepth

1. 创建一个简单场景。
2. 放置几个距离摄像机不同的 Cube 或 Sphere。
3. 在视口中打开 Buffer Visualization。
4. 选择 SceneDepth。

观察：

- 把物体向摄像机移动，深度可视化如何变化？
- 把物体远离摄像机，深度可视化如何变化？
- 修改物体的 BaseColor，SceneDepth 是否随之变化？
- 移动摄像机，整个深度图如何变化？

注意：SceneDepth 的可视化通常会对深度进行转换或显示映射，不一定是 Depth Buffer 原始数值的直接显示。

## 实验二：观察遮挡关系

1. 放置两个不透明物体。
2. 让它们在摄像机视角中部分重叠。
3. 前后移动物体。
4. 观察哪个表面最终可见。

再改变物体的绘制顺序或相关场景条件，理解深度测试不是简单地“后画覆盖先画”。

## 实验三：观察 Roughness 与 SceneDepth 的区别

分别切换：

- Roughness
- SceneDepth

观察两者代表的数据不同：

```text
Roughness：材质表面属性
SceneDepth：表面相对摄像机的深度信息
```

这可以帮助区分 GBuffer 中的表面属性和独立深度资源。

## 实验四：测试 Depth PrePass

在项目的 Rendering 设置中查找 Early Z Pass / Early Z-pass 相关选项。

不同 UE 版本的选项名称和可用模式可能不同。

可以在固定场景、固定分辨率下，对比开启和关闭深度预处理后的 GPU 时间。

使用：

```text
ProfileGPU
```

观察 PrePass 和 BasePass 的耗时变化。

注意：

- 关闭主动 Depth PrePass，不代表 GPU 的 Early-Z 硬件优化一定关闭。
- 开启 PrePass 后，总耗时也不一定更低。
- 测试时需要保持场景、摄像机、分辨率和其他设置一致。
- 应多次运行并比较稳定结果，不要只看一次数据。

# 十三、本节知识结构总结

现在把整节课的知识连起来。

## 1. 深度如何产生？

```text
Vertex Position
    ↓
坐标变换
    ↓
Projection
    ↓
Clip Space / NDC
    ↓
Rasterization
    ↓
Fragment Depth
```

## 2. 深度如何参与可见性判断？

```text
Fragment Depth
    ↓
Depth Test
    ↓
通过？
    ├── 是：继续后续处理
    └── 否：丢弃相关结果
```

如果开启深度写入，满足条件的 Fragment 还可以更新 Depth Buffer。

## 3. 如何减少无用的着色计算？

```text
Early-Z
    ↓
尽可能在 Pixel Shader 之前进行深度测试
    ↓
提前淘汰确定被遮挡的 Fragment
```

## 4. 如何提前准备深度？

```text
Depth PrePass
    ↓
提前处理相关几何体
    ↓
生成 Depth Buffer
    ↓
正式 Base Pass 利用已有深度
```

## 5. 如何改善深度精度？

```text
透视深度非线性
    ↓
深度精度分布不均
    ↓
可能产生 Z-Fighting
    ↓
使用合适的深度格式和 Reverse-Z 等方案改善
```

# 十四、最后需要真正记住的概念

| 概念 | 一句话理解 |
|---|---|
| Depth | 描述表面相对摄像机的深度 |
| Depth Buffer | 保存深度值的 GPU 资源 |
| Depth Test | 比较当前 Fragment 与已有深度 |
| Depth Write | 把通过条件的深度写入缓冲区 |
| Early-Z | 尽可能提前执行深度测试 |
| Late-Z | 在较晚阶段执行深度测试 |
| Depth PrePass | 额外执行一个 Pass，提前准备深度 |
| Z-Fighting | 深度精度不足或表面过于接近时出现的深度冲突 |
| Reverse-Z | 反转深度映射，配合浮点深度格式改善精度 |

本节最核心的逻辑是：

> **Depth Buffer 记录深度，Depth Test 判断遮挡，Early-Z 尽可能提前淘汰不可见片元，Depth PrePass 可以提前准备深度数据，而 Reverse-Z 则用于改善深度精度。**
