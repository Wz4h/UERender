# UE 渲染系统 01：屏幕上的一张图片到底是什么？

## 一、本节目标

这是整个 UE 渲染系统系列的第一节。

这一节暂时不讲：

- 3D 模型
- 三角形
- 摄像机
- 光栅化
- Shader
- UE Render Thread
- RHI

因为在研究“UE 怎么渲染 3D 世界”之前，我们需要先搞清楚一个更加基础的问题：

> **电脑最终到底要生成什么东西，显示器才能把画面显示出来？**

这一节只需要建立下面几个最基础的概念：

1. 什么是像素
2. 什么是分辨率
3. 颜色在计算机里怎么表示
4. 一张二维图片在计算机里是什么
5. 什么是一帧
6. 什么是 FPS
7. 什么是渲染
8. CPU / GPU 为什么要生成画面
9. 生成好的画面大概是怎么交给显示器的
10. FPS 和显示器刷新率有什么区别

这一节最后，我们会留下一个问题：

> 如果一张普通二维图片很好理解，那么一个 3D 游戏，是怎么生成这张二维图片的？

这会成为下一节的内容。

---

# 二、从显示器开始

我们平时看到的游戏画面非常复杂。

例如：

- 人物
- 建筑
- 天空
- UI
- 文字
- 光照
- 阴影
- 粒子
- 特效

但是显示器并不理解：

> “这里有一个人物。”

也不理解：

> “这里是一栋房子。”

从一个非常基础的角度来看，显示器最终需要处理的是：

> **屏幕上每一个位置应该显示什么颜色。**

---

# 三、什么是像素

屏幕可以先理解成一个巨大的二维网格。

这个网格中的每一个小位置，就是：

# Pixel —— 像素

例如一个非常小的屏幕：

```text
[ ][ ][ ][ ]
[ ][ ][ ][ ]
[ ][ ][ ][ ]
```

如果它横向有 4 个像素，纵向有 3 个像素，那么它的分辨率就是：

```text
4 × 3
```

真实显示器当然要大得多。

例如：

```text
1920 × 1080
```

表示：

```text
横向：1920 个像素
纵向：1080 个像素
```

总像素数量：

```text
1920 × 1080
= 2,073,600
```

也就是大约：

> 207 万个像素。

所以，当我们说一块屏幕是 1080P 时，可以先粗略理解成：

> 屏幕上存在大约两百万个需要显示颜色的位置。

---

# 四、每个像素到底显示什么

既然屏幕由像素组成，那么接下来最重要的问题就是：

> 一个像素怎么知道自己应该显示什么颜色？

最常见的一种颜色表示方式是：

# RGB

分别代表：

```text
R = Red
G = Green
B = Blue
```

例如：

```text
RGB(255, 0, 0)
```

可以表示红色。

```text
RGB(0, 255, 0)
```

可以表示绿色。

```text
RGB(0, 0, 255)
```

可以表示蓝色。

```text
RGB(255, 255, 255)
```

可以表示白色。

```text
RGB(0, 0, 0)
```

可以表示黑色。

所以可以先把一个像素理解成：

```text
一个位置
+
一个颜色
```

例如：

```text
Pixel(100, 200)
=
RGB(255, 0, 0)
```

意思就是：

> 图片中坐标为 `(100, 200)` 的位置是红色。

---

# 五、一张图片本质上是什么

现在假设我们只有一张非常小的：

```text
4 × 4
```

图片。

它可能长这样：

```text
[红][红][蓝][蓝]
[红][绿][绿][蓝]
[黑][黑][白][白]
[黑][黄][黄][白]
```

我们人看到它，会把这些颜色组合起来理解成一张完整图片。

但是从计算机的角度，可以先把它理解成：

```text
(0,0) = 红
(1,0) = 红
(2,0) = 蓝
(3,0) = 蓝

(0,1) = 红
(1,1) = 绿
(2,1) = 绿
(3,1) = 蓝

……
```

也就是说：

> **一张二维图片，本质上可以理解成大量位置对应大量颜色数据。**

这句话非常重要。

以后无论我们研究：

- 2D 游戏
- 3D 游戏
- UI
- 后处理
- 光照
- Shader

最终都绕不开：

> 我们需要生成一张这样的二维颜色结果。

---

# 六、图片在内存里是什么样

假设我们使用非常简单的 RGB 数据。

那么一个像素可能需要保存：

```text
R
G
B
```

三个数值。

例如红色：

```text
255 0 0
```

绿色：

```text
0 255 0
```

蓝色：

```text
0 0 255
```

那么一张图片在内存中，可以粗略想象成一长串数据：

```text
255 0   0
255 0   0
0   0   255
0   0   255
...
```

也可以理解成：

```text
[RGB][RGB][RGB][RGB]...
```

一行接着一行。

---

# 七、RGBA 是什么

实际使用中，我们经常还会看到：

# RGBA

相比 RGB，多了一个：

```text
A = Alpha
```

Alpha 通常用来描述透明度等信息。

例如：

```text
RGBA(255, 0, 0, 255)
```

可以理解成完全不透明的红色。

如果使用常见的 RGBA8 格式：

```text
R = 1 Byte
G = 1 Byte
B = 1 Byte
A = 1 Byte
```

那么一个像素就是：

```text
4 Byte
```

一张：

```text
1920 × 1080
```

的 RGBA8 图片，大约需要：

```text
1920 × 1080 × 4
= 8,294,400 Byte
```

大约：

```text
8.3 MB
```

这可以帮助我们建立一个非常重要的印象：

> 一张看起来非常复杂的游戏画面，在计算机中最终仍然需要落到大量颜色数据上。

---

# 八、PNG 和 JPG 文件是不是就这样存的？

这里需要特别注意。

我们平时看到的：

```text
.png
.jpg
.jpeg
```

文件，一般不会简单地把所有 RGB 数值原封不动排列在文件里。

因为这样文件会很大。

PNG、JPG 都会使用自己的：

```text
压缩
编码
文件格式
```

所以如果直接用十六进制编辑器打开 JPG：

> 并不会直接看到一排排直观的 RGB 数据。

一般需要先：

```text
PNG / JPG 文件
↓
解码
↓
得到真正的像素数据
```

解码以后，我们才可以去读取：

```text
Pixel(100,100)
=
RGB(...)
```

---

# 九、实验一：观察一张真实图片

这一节可以做第一个实验。

随便找一张：

```text
PNG
或者
JPG
```

图片。

## 第一步：正常观察

比如是一张风景图。

我们眼睛看到的是：

- 天空
- 山
- 草地
- 建筑

这是人脑对图片内容的理解。

---

## 第二步：不断放大

一直放大。

最后会看到一个个明显的小方格。

这些就是图片里的像素。

原来我们感觉连续的天空：

```text
蓝色渐变
```

实际上可以理解成：

```text
一个像素
+
一个像素
+
一个像素
+
……
```

每一个位置都有稍微不同的颜色。

---

## 第三步：读取一个具体像素

例如读取：

```text
Pixel(100,100)
```

可能得到：

```text
RGB(136, 182, 220)
```

再读取旁边：

```text
Pixel(101,100)
```

可能得到：

```text
RGB(137, 183, 221)
```

虽然我们眼睛看到的是一整片连续天空，

但计算机处理的是：

> 一个个具体位置的颜色数据。

---

# 十、什么是一帧

现在我们已经知道：

> 一张图片就是大量像素颜色。

但是游戏不是只显示一张图片。

例如一个人物正在奔跑。

实际上可以先粗略理解成：

```text
第 1 张图片
↓
第 2 张图片
↓
第 3 张图片
↓
第 4 张图片
↓
……
```

这些图片连续快速显示以后，我们就会感觉：

> 画面正在运动。

其中每一张完整的画面就叫：

# Frame —— 帧

---

# 十一、什么是 FPS

FPS：

```text
Frames Per Second
```

意思就是：

> 每秒产生多少帧画面。

例如：

```text
60 FPS
```

可以粗略理解成：

```text
1 秒钟
↓
产生约 60 张完整图片
```

如果游戏是：

```text
120 FPS
```

那就是：

```text
1 秒
↓
约 120 张画面
```

所以游戏运行时，并不是有一个“会动的画面”。

从一个非常基础的角度来说，是：

> **电脑在不断生成新的二维图片。**

---

# 十二、现在可以第一次定义“渲染”

到这里，我们终于可以讨论：

# Rendering —— 渲染

第一节先不要把它定义得过于复杂。

最基础的理解：

> **渲染，就是生成最终画面的过程。**

比如现在我们想生成这样一张图片：

```text
左边是黑色
右边是白色
中间逐渐过渡
```

我们可以写一个规则：

```text
越靠左
颜色越暗

越靠右
颜色越亮
```

然后：

```text
对每个位置计算颜色
↓
把所有颜色组合起来
↓
得到一张二维图片
```

这已经是一个非常基础的渲染过程。

注意：

> **渲染不等于 3D。**

2D 图片、UI、3D 场景、后处理等，最终都会参与画面的生成。

---

# 十三、实验二：自己生成一张图片

我们可以自己生成一张：

```text
256 × 256
```

图片。

规则非常简单：

```text
像素越靠右
颜色越亮
```

例如：

```text
左边
RGB(0,0,0)

↓

中间
RGB(128,128,128)

↓

右边
RGB(255,255,255)
```

最终会生成一个：

```text
黑 → 灰 → 白
```

的渐变。

这里发生的事情非常简单：

```text
遍历每一个像素位置
↓
根据位置计算颜色
↓
把结果写进图片
```

现在我们没有：

- 模型
- 三角形
- 灯光
- 摄像机

但我们依然：

> 生成了一张最终画面。

所以这就是为什么：

> **“渲染”不能简单理解成“画 3D 模型”。**

它更底层的目标是：

> 生成最终图像。

---

# 十四、为什么需要 GPU

现在假设我们的图片是：

```text
1920 × 1080
```

一帧就有：

```text
约 207 万像素
```

如果每秒：

```text
60 FPS
```

那么一秒对应：

```text
207 万 × 60
≈ 1.24 亿
```

个像素位置。

而真实游戏中，一个像素颜色通常并不是简单地：

```text
x 越大越亮
```

真实渲染可能需要进行大量复杂计算。

因此：

> 画面生成过程存在非常大量、非常适合并行执行的计算。

这正是 GPU 特别擅长的领域。

---

# 十五、CPU 和 GPU 第一印象

这一节不深入 GPU 架构。

只建立一个非常粗略的认知。

## CPU

CPU 很适合处理：

```text
复杂逻辑
程序流程
大量条件判断
游戏逻辑
数据组织
```

例如：

```text
玩家按下攻击
↓
判断能不能攻击
↓
查找目标
↓
计算伤害
↓
修改血量
```

---

## GPU

GPU 特别擅长：

> 同时处理大量类似计算。

例如：

```text
计算像素 A
计算像素 B
计算像素 C
计算像素 D
……
```

所以可以先记：

```text
CPU
偏向复杂逻辑和数据组织

GPU
偏向大量并行计算
```

这只是第一印象。

后面的课程会专门研究 GPU 到底是怎样工作的。

---

# 十六、生成好的图片放在哪里

现在假设：

> GPU 已经计算好这一帧画面了。

最终我们需要有一块地方保存：

```text
这一帧最终每个位置的颜色
```

可以先简单理解成：

> 一块用于保存二维图像结果的内存。

例如：

```text
[红][红][蓝][蓝]
[红][绿][绿][蓝]
[黑][黑][白][白]
```

真实图形系统中会出现很多相关概念：

- Render Target
- Color Buffer
- Framebuffer
- Back Buffer

这些概念之间并不完全相同。

第一节不展开。

现在只需要建立一个印象：

> **渲染产生的结果最终需要存成一张二维图像。**

---

# 十七、生成图片和显示图片不是同一件事

这是一个非常重要的概念。

假设 GPU 已经生成了：

```text
Frame 100
```

生成画面是一件事。

而：

> 显示器什么时候把这张画面显示出来

是另外一件事。

可以粗略理解成：

```text
CPU / GPU
↓
生成下一帧二维图片
↓
放入用于显示的缓冲区
↓
Present
↓
显示系统
↓
显示器刷新
↓
用户看到这一帧
```

因此：

> 渲染画面和显示画面是两个相互配合但不同的过程。

---

# 十八、为什么需要 Back Buffer

可以先做一个思想实验。

假设只有一张画布。

显示器现在正在读取：

```text
旧画面
```

但 GPU 同时开始往同一张画面里写：

```text
新画面
```

那么显示器可能读到：

```text
上面还是旧画面
下面已经变成新画面
```

这显然会出问题。

所以现代图形系统通常会使用多个缓冲区。

最简单的理解：

```text
Front Buffer
=
现在正在显示的画面
```

```text
Back Buffer
=
正在准备的下一帧画面
```

GPU 可以在 Back Buffer 中准备：

```text
Frame N+1
```

而显示系统仍然使用：

```text
Frame N
```

当新画面准备完成以后，再进行交换或提交。

---

# 十九、什么是 Present

可以暂时把：

# Present

理解成：

> 告诉显示系统：“这一帧已经准备好了，可以拿去显示了。”

粗略流程：

```text
GPU 渲染
↓
Back Buffer
↓
Present
↓
显示系统
↓
显示器
```

真实情况下还会涉及：

- Swap Chain
- VSync
- 显示驱动
- 操作系统
- Display Engine

第一节全部不深入。

先知道：

> 渲染结束之后，还需要把最终画面交给显示系统。

---

# 二十、FPS 和刷新率不是一个东西

这时候可以自然引出两个非常容易混淆的概念。

## FPS

FPS 表示：

> 游戏产生新画面的速度。

例如：

```text
120 FPS
```

代表游戏大约每秒生成：

```text
120 帧
```

---

## Hz

显示器刷新率一般使用：

```text
Hz
```

例如：

```text
60Hz
144Hz
240Hz
```

可以粗略理解成：

> 显示器每秒能够刷新多少次。

所以：

```text
FPS
=
游戏生成画面的速度
```

```text
Hz
=
显示器刷新画面的速度
```

它们不是同一个东西。

---

# 二十一、为什么会出现撕裂

这里可以浅浅留一个现象。

如果：

> GPU 提交新画面的时机

和：

> 显示器读取画面的时机

没有很好协调，

显示器的一次刷新可能出现：

```text
上半部分
=
旧帧

下半部分
=
新帧
```

于是画面出现明显断层。

这就是：

# Screen Tearing —— 画面撕裂

为了解决或者控制这些问题，后面会继续涉及：

- VSync
- Swap Chain
- Double Buffer
- Triple Buffer

第一节只留下印象，不深入。

---

# 二十二、第一节整体流程

现在我们可以把这一节所有内容连接起来。

注意，这还不是完整的“3D 图形管线”。

这里只是在讲：

> 一张最终二维画面是怎样生成并被显示出来的。

流程可以粗略理解为：

```text
程序需要生成一帧画面
        ↓
CPU / GPU 执行计算
        ↓
确定大量屏幕位置的颜色
        ↓
生成一张二维图像
        ↓
保存到用于显示的图像缓冲
        ↓
Present
        ↓
显示系统
        ↓
显示器刷新
        ↓
用户看到这一帧
```

然后：

```text
继续生成下一帧
↓
继续显示
↓
继续生成
↓
继续显示
……
```

最终形成我们看到的动态游戏画面。

---

# 二十三、这一节最重要的三个认识

第一节不要求记住很多名词。

只需要真正理解下面三件事。

## 第一：显示器最终显示的是二维像素

无论游戏有多复杂：

```text
人物
建筑
UI
光照
特效
```

最后都必须变成：

> 一张二维的像素颜色结果。

---

## 第二：渲染的最终目标是生成画面

第一节可以先记：

```text
Rendering
=
生成最终图像的过程
```

所以：

> 渲染不等于 3D。

---

## 第三：生成画面和显示画面不是同一件事

```text
CPU / GPU
负责生成画面

↓

显示系统 / 显示器
负责把画面显示出来
```

两者共同作用，我们才最终看到游戏。
