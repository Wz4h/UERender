# UE 渲染系统 01：屏幕上的一帧画面到底是怎么来的？

## 一、本节目标

这一节不进入 UE 源码，也不要求任何图形学基础。

目标是先建立最基础的渲染认知：

1. 屏幕到底是怎么显示画面的
2. 什么是像素
3. 什么是一帧画面
4. 什么是 Framebuffer
5. FPS 和显示器刷新率有什么区别
6. 什么是渲染
7. CPU 和 GPU 分别负责什么
8. 3D 模型在计算机里到底是什么
9. GPU 如何大致把 3D 世界变成二维画面
10. Shader 和光栅化分别处于什么位置

学完这一节之后，希望能够理解下面这条最基础的流程：

```text
3D 场景数据
    ↓
CPU 准备数据
    ↓
GPU 执行渲染
    ↓
生成二维像素结果
    ↓
Framebuffer
    ↓
显示系统
    ↓
屏幕
```

---

# 二、屏幕到底是什么

在讨论 UE 怎么渲染之前，先考虑一个更加基础的问题：

> 游戏最后为什么能够出现在屏幕上？

显示器看起来能够显示人物、场景、文字、光照等各种复杂内容。

但从计算机的角度来看，屏幕最终只是一个巨大的二维网格。

这个网格由大量：

> Pixel —— 像素

组成。

例如一块分辨率为：

```text
1920 × 1080
```

的显示器，可以简单理解为：

```text
横向 1920 个像素
纵向 1080 个像素
```

总像素数量约为：

```text
1920 × 1080
= 2,073,600
```

也就是大约：

> 207 万个像素。

---

# 三、像素是什么

可以暂时把一个像素理解为：

> 屏幕上一个非常小的颜色点。

每个像素最终都需要确定自己的颜色。

最常见的一种表示方式就是 RGB：

```text
R = Red   红色
G = Green 绿色
B = Blue  蓝色
```

例如：

```text
RGB(255, 0, 0)
```

表示红色。

```text
RGB(0, 255, 0)
```

表示绿色。

```text
RGB(0, 0, 255)
```

表示蓝色。

```text
RGB(255, 255, 255)
```

表示白色。

因此，从一个非常简化的角度来看，一张图片其实就是：

```text
第 1 个像素是什么颜色
第 2 个像素是什么颜色
第 3 个像素是什么颜色
……
第 2073600 个像素是什么颜色
```

把所有像素的颜色组合起来，我们就得到了一张完整的二维图片。

---

# 四、什么叫“一帧”

游戏并不是只生成一张图片。

它实际上是在不停地生成新的图片。

例如：

```text
第 1 帧
第 2 帧
第 3 帧
第 4 帧
……
```

这些图片快速连续播放之后，人眼就会感觉画面正在运动。

这和动画、电影的基本原理是类似的。

因此：

> Frame —— 帧

可以先理解为：

> 游戏在某一个时刻生成的一张完整画面。

例如游戏运行在：

```text
60 FPS
```

FPS 的意思是：

> Frames Per Second

也就是：

> 每秒生成多少帧画面。

60 FPS 可以简单理解为：

```text
1 秒钟
↓
生成约 60 张画面
```

---

# 五、Framebuffer 是什么

现在出现一个问题。

假设 GPU 已经算出了：

```text
像素 1 = 红色
像素 2 = 黑色
像素 3 = 蓝色
……
```

这些结果总得先存到一个地方。

这时候就可以先认识：

# Framebuffer

现阶段可以把它简单理解为：

> 用来保存一帧图像结果的一块内存区域。

例如我们假设屏幕只有 4×4 个像素：

```text
[红][红][蓝][蓝]
[红][绿][绿][蓝]
[黑][黑][白][白]
[黑][红][白][白]
```

这些颜色数据就可以存放在 Framebuffer 中。

所以可以把渲染结果粗略理解为：

```text
GPU
↓
计算每个像素最终应该是什么颜色
↓
写入 Framebuffer
```

Framebuffer 里最终保存的，本质上就是：

> 一张等待显示出来的二维图片。

---

# 六、画面是怎么真正显示到屏幕上的

现在已经有了一张完整图片。

接下来显示系统需要把它送到显示器。

可以先粗略理解成：

```text
GPU
↓
生成一帧
↓
Framebuffer
↓
显示系统
↓
显示器
↓
屏幕上的像素显示对应颜色
```

因此：

> 游戏渲染出一张图片，显示器再把这张图片显示出来。

然后游戏继续生成下一张。

于是不断循环：

```text
生成第 1 帧
↓
显示

生成第 2 帧
↓
显示

生成第 3 帧
↓
显示
```

最终形成连续运动的游戏画面。

---

# 七、FPS 和 Hz 有什么区别

这里很容易混淆两个概念：

```text
FPS
```

和：

```text
Hz
```

## FPS

FPS 主要描述：

> 游戏每秒生成了多少帧。

例如：

```text
60 FPS
```

表示大约每秒生成 60 张新画面。

---

## Hz

Hz 通常用来描述显示器的刷新率。

例如：

```text
60Hz
```

可以简单理解为：

> 显示器每秒刷新大约 60 次。

例如：

```text
144Hz
```

表示显示器能够以更高的频率更新屏幕。

---

## 二者不是一回事

例如：

```text
游戏：120 FPS
显示器：60Hz
```

说明游戏可能每秒产生大约 120 帧，但显示器本身每秒只能刷新约 60 次。

反过来：

```text
游戏：40 FPS
显示器：144Hz
```

显示器虽然能刷新得很快，但是游戏没有足够多的新画面提供给它。

因此：

```text
FPS
=
游戏生成画面的速度
```

```text
Hz
=
显示器刷新画面的速度
```

---

# 八、为什么会出现画面撕裂

这里可以简单认识一个现象：

> Screen Tearing —— 画面撕裂。

假设显示器正在读取一张旧画面：

```text
旧帧
```

但是读取到一半的时候，GPU 已经准备好了下一张画面，并把显示目标切换过去。

那么显示器这一轮刷新可能出现：

```text
屏幕上半部分
=
旧帧

屏幕下半部分
=
新帧
```

于是我们看到画面中间出现明显的断层。

这就是最基本的画面撕裂现象。

为了处理这种问题，现代图形系统中还会涉及：

- VSync
- Double Buffering
- Triple Buffering
- Swap Chain
- Present

这些内容第一节先不展开。

暂时只需要知道：

> GPU 生成画面和显示器读取画面之间，也需要进行协调。

---

# 九、现在才进入“渲染”

到这里，我们已经知道最终目标是什么了：

> 显示器需要的是一张二维像素图片。

但游戏世界并不是二维图片。

例如 UE 场景里可能存在：

- 一个角色
- 一把武器
- 一栋建筑
- 一盏灯
- 天空
- 摄像机
- 粒子
- 地面

这些东西本质上都是各种：

> 场景数据。

于是就出现整个渲染系统最核心的问题：

```text
游戏拥有一个 3D 世界

↓

显示器却只能显示二维像素

↓

怎么把 3D 世界变成二维图片？
```

这个过程就是：

# Rendering —— 渲染

现阶段可以把渲染定义为：

> 根据场景中的模型、摄像机、材质、灯光等数据，计算出最终二维画面的过程。

因此：

```text
3D 场景
↓
渲染
↓
二维图片
↓
屏幕
```

---

# 十、为什么需要 GPU

既然渲染也是计算，那么为什么不能全部交给 CPU？

理论上当然可以。

但问题在于：

> 图形渲染需要执行非常大量的计算。

以 1920×1080 为例：

```text
约 207 万像素
```

如果游戏运行在：

```text
60 FPS
```

那么一秒钟对应的像素数量大约就是：

```text
207 万 × 60
≈ 1.24 亿
```

而真实游戏渲染远远不只是简单地给这些像素填颜色。

还可能涉及：

- 几百万甚至更多顶点
- 大量三角形
- 材质计算
- 灯光
- 阴影
- 反射
- 透明
- 粒子
- 后处理
- 抗锯齿
- 全局光照

于是就需要一种特别擅长执行大量类似计算的硬件。

这就是：

# GPU

Graphics Processing Unit

图形处理器。

---

# 十一、CPU 和 GPU 有什么区别

现阶段不用深入硬件架构。

可以先用一个非常粗略的模型理解。

## CPU

CPU 更擅长：

> 相对复杂、步骤和分支很多的逻辑任务。

例如游戏逻辑：

```text
玩家按下鼠标
↓
检查当前状态
↓
技能是否处于冷却
↓
是否拥有足够法力值
↓
确定攻击目标
↓
计算伤害
↓
修改生命值
↓
触发死亡事件
```

这种逻辑非常复杂，而且不同任务之间差异很大。

CPU 很适合完成这种工作。

---

## GPU

GPU 更擅长：

> 同时执行大量非常相似的计算。

例如：

```text
计算这个顶点的位置
计算另一个顶点的位置
计算第三个顶点的位置
……
```

或者：

```text
计算这个像素的颜色
计算另一个像素的颜色
计算第三个像素的颜色
……
```

图形渲染中恰好存在大量这样的计算。

因此 GPU 非常适合渲染。

现阶段可以先粗略记住：

```text
CPU
↓
擅长复杂逻辑和数据组织
```

```text
GPU
↓
擅长大量并行计算
```

这只是方便初学者建立认知，并不是 CPU 和 GPU 的严格定义。

---

# 十二、3D 模型到底是什么

现在开始看：

> GPU 到底在渲染什么？

比如 UE 里放一个人物模型。

我们作为人，会认为这是：

> 一个角色。

但是 GPU 并不知道：

```text
人
武器
房子
树
汽车
```

这些概念。

GPU 看到的主要是：

> 数据。

3D 模型最基础的数据之一就是：

# Vertex —— 顶点

一个顶点最基础的信息是它在空间中的位置。

例如：

```text
Vertex 0

X = 0
Y = 0
Z = 0
```

另外一个：

```text
Vertex 1

X = 100
Y = 0
Z = 0
```

这些就是 3D 世界中的点。

---

# 十三、顶点组成三角形

只有一个点当然没有办法形成一个物体表面。

因此 GPU 会把多个顶点组织成：

# Triangle —— 三角形

例如：

```text
       A
      / \
     /   \
    /     \
   B-------C
```

三个顶点组成一个三角形。

大量三角形再组合到一起：

```text
顶点
↓
三角形
↓
大量三角形
↓
模型表面
```

所以从非常基础的角度来说：

> 一个 3D 模型可以看成大量顶点和三角形组成的几何表面。

例如：

```text
一个 Cube
```

看起来是一个完整的立方体。

但是开启 Wireframe 之后就会发现：

> 它实际上由多个三角形组成。

---

# 十四、为什么 3D 图形大量使用三角形

三个不共线的点一定能够确定一个平面。

因此三角形是一个非常稳定、非常方便进行计算的几何单位。

例如一个四边形：

```text
A------B
|      |
|      |
D------C
```

四个点并不一定处于同一个平面。

其中一个点可能翘起来。

但是：

> 一个三角形的三个点一定能够确定一个平面。

因此现代实时图形渲染大量使用三角形作为基本图元。

这就是为什么 UE 中经常能够看到：

```text
Triangles
```

或者：

```text
Tris
```

这样的统计数据。

---

# 十五、顶点不只有位置

真实游戏里的顶点通常并不只保存 Position。

还可能携带很多信息。

例如：

```text
Position
位置
```

```text
Normal
法线
```

```text
UV
纹理坐标
```

```text
Vertex Color
顶点颜色
```

等等。

这些东西之后都会进入材质和 Shader 的计算。

第一节暂时不用理解具体原理。

现在只需要知道：

> 顶点不仅代表空间中的一个位置，它还可以携带很多渲染需要的数据。

---

# 十六、3D 世界怎么出现在二维屏幕上

现在遇到渲染系统非常重要的一个问题。

游戏世界通常使用：

```text
X
Y
Z
```

三个维度。

也就是说：

> 它是 3D 的。

但是屏幕只有：

```text
X
Y
```

也就是二维。

假设世界中有一个点：

```text
X = 100
Y = 500
Z = 200
```

最终必须找到它在屏幕上的位置，例如：

```text
屏幕 X = 650
屏幕 Y = 420
```

因此渲染过程中必须完成：

```text
3D 坐标
↓
转换
↓
2D 屏幕位置
```

---

# 十七、Camera —— 摄像机

这个过程需要：

# Camera

摄像机可以理解为：

> 我们从什么位置、什么方向观察这个 3D 世界。

摄像机需要描述很多信息，例如：

```text
摄像机在哪里
```

```text
摄像机朝哪里
```

```text
视野有多宽
```

```text
哪些东西能够被看到
```

因此：

```text
3D 世界
+
摄像机
↓
从当前视角观察到的结果
```

之后会进一步学习：

- World Space
- View Space
- Clip Space
- Projection
- Perspective
- View Matrix
- Projection Matrix

但第一节暂时不展开。

现在只需要知道：

> 摄像机决定我们从哪里观察这个三维世界。

---

# 十八、三角形投影到屏幕后还不够

假设一个三角形最终已经来到屏幕空间：

```text
       A
      / \
     /   \
    /     \
   B-------C
```

但屏幕并不认识：

> 三角形。

屏幕最终只有：

> 像素。

例如：

```text
[][][][][][][]
[][][][][][][]
[][][][][][][]
[][][][][][][]
```

因此接下来还需要确定：

> 这个三角形到底覆盖了哪些像素？

例如：

```text
[][][X][][][]
[][X][X][][]
[][X][X][X][]
[X][X][X][X][]
```

这就引出了：

# Rasterization —— 光栅化

第一节可以先简单理解为：

> 光栅化就是把三角形转换成它在屏幕上覆盖哪些像素的过程。

更准确的定义之后再学习。

---

# 十九、知道覆盖哪些像素以后，还没有结束

光栅化之后，我们只是知道：

```text
这个像素属于这个三角形
```

但是还不知道：

> 这个像素最终应该是什么颜色。

例如一个人物的脸：

为什么有些地方亮？

为什么有些地方暗？

为什么皮肤是肤色？

为什么眼睛会反光？

为什么衣服是红色？

最终颜色可能受到很多因素影响：

```text
材质
贴图
灯光
法线
阴影
摄像机方向
反射
……
```

渲染系统最终需要根据这些数据计算：

```text
这个像素最终是什么颜色
```

例如：

```text
R = 210
G = 160
B = 140
```

然后这个颜色才能被写进最终画面。

---

# 二十、Shader 是什么

这时候第一次引入：

# Shader

现阶段可以把 Shader 简单理解为：

> 运行在 GPU 上，用来执行渲染计算的小程序。

Shader 有很多种。

第一节只需要知道其中两个最经典的：

- Vertex Shader
- Pixel Shader

---

## Vertex Shader

Vertex Shader 主要处理：

> 顶点。

例如模型拥有：

```text
Vertex 0
Vertex 1
Vertex 2
Vertex 3
……
```

这些顶点会被送入 Vertex Shader。

Vertex Shader 最经典的工作之一就是：

> 对顶点的位置进行变换。

最终让顶点来到 GPU 后续渲染流程需要的位置。

可以先简单理解成：

```text
3D 顶点
↓
Vertex Shader
↓
得到用于屏幕绘制的位置
```

---

# 二十一、Pixel Shader

经过光栅化之后，会产生大量需要处理的像素。

Pixel Shader 负责进行像素相关的计算。

例如：

```text
读取材质
读取贴图
计算光照
计算颜色
```

最终可能得到：

```text
RGB(150, 80, 30)
```

然后写入最终的渲染目标。

因此第一节可以先形成一个极度简化的流程：

```text
模型顶点
↓
Vertex Shader
↓
三角形位置确定
↓
Rasterization
↓
找到三角形覆盖的像素
↓
Pixel Shader
↓
计算像素颜色
```

---

# 二十二、最终又回到了屏幕

现在整条链路终于能够闭环。

最开始，我们的问题是：

> 屏幕上的一帧画面到底是怎么来的？

现在可以给出一个非常简化的答案：

```text
3D 场景数据
│
├─ 模型
├─ 材质
├─ 灯光
└─ 摄像机
     ↓

CPU
准备和组织需要渲染的数据
     ↓

GPU
开始进行大量渲染计算
     ↓

Vertex Shader
处理顶点
     ↓

三角形
     ↓

Rasterization
确定三角形覆盖哪些像素
     ↓

Pixel Shader
计算像素颜色
     ↓

Framebuffer
保存最终二维画面
     ↓

显示系统
     ↓

显示器
     ↓

我们看到游戏画面
```

这就是第一节最重要的一张图。

Cube

# 二十四、实验二：开启 Wireframe

在 UE View Mode 中切换到：

```text
Wireframe
```

观察 Cube。

这时候可以非常直观地看到：

> 原来看起来连续完整的物体表面，实际上由大量三角形组成。

这个实验可以把：

```text
模型
=
大量三角形
```

从一个抽象概念变成非常直观的画面。

# 二十五、实验三：移动模型

在 UE 中移动 Cube。

修改：

```text
Transform
```

例如改变：

```text
Location
```

可以观察到：

> Cube 在屏幕上的位置也发生了变化。

背后最基本的逻辑就是：

```text
模型的 3D 世界位置发生变化
↓
顶点位置发生相应变换
↓
重新经过渲染流程
↓
投影到新的屏幕位置
↓
生成新的画面
```

# 二十六、实验四：移动灯光

保持：

```text
Cube
```

完全不动。

然后旋转 Directional Light。

这时候可以看到：

> 模型本身没有变化，但是最终画面的颜色、明暗却发生了变化。

这说明：

```text
模型几何
```

并不是决定最终画面的唯一因素。

最终像素颜色还会受到：

```text
灯光
材质
法线
阴影
```

等因素影响。

这也为后面的课程留下问题：

> GPU 到底是怎么计算光照的？

# 二十七、第一节一定要区分几个概念

## 模型不是图片

模型主要描述：

> 三维几何数据。

---

## 贴图不是材质

贴图通常只是：

> 一份图像或数据资源。

材质则描述：

> 一个物体表面应该如何参与渲染。

---

## Shader 不是贴图

Shader 是：

> GPU 执行的程序。

---

## GPU 不是显示器

GPU：

> 负责大量计算，生成画面。

显示器：

> 负责把结果显示出来。

---

## FPS 不等于刷新率

FPS：

> 游戏生成帧的速度。

Hz：

> 显示器刷新画面的速度。

第一节不用记大量细节。

## 1. 什么是渲染

```text
渲染
=
把场景数据计算成最终二维画面的过程
```

---

## 2. 什么是一帧

```text
Frame
=
某一个时刻生成的一张完整画面
```

---

## 3. 屏幕是什么

```text
屏幕
=
由大量像素构成的二维网格
```

---

## 4. Framebuffer 是什么

可以暂时理解为：

```text
Framebuffer
=
保存一帧图像结果的内存区域
```

---

## 5. CPU 和 GPU 的基本分工

```text
CPU
=
复杂逻辑 + 数据组织
```

```text
GPU
=
大量并行计算
```

---

## 6. 模型是什么

```text
模型
≈
顶点 + 三角形 + 其他渲染数据
```

---

## 7. 什么是光栅化

```text
Rasterization
≈
确定三角形覆盖了哪些屏幕像素
```

---

## 8. 什么是 Shader

```text
Shader
=
运行在 GPU 上执行渲染计算的程序
```

---

## 9. Vertex Shader 做什么

可以暂时理解为：

```text
处理顶点
↓
计算顶点最终需要处于什么位置
```

---

## 10. Pixel Shader 做什么

可以暂时理解为：

```text
处理像素
↓
计算最终颜色
```
